# RAG Search — Architecture & Constraints

> Nevis Backend Home Task · WealthTech search API across clients & documents.
> Durable record of agreed constraints and decisions. Source of truth for implementation.
> Status: **Build mode** · v1 `/search` = hybrid (client FTS + document RRF fusion) · All v1 decisions locked.

---

## 1. Overview

A FastAPI service that lets advisors search across **clients** and their **documents**. The API supports:

- **Client matches** in email / name / description  (substring)
- **Document matches** by semantic similarity over content (e.g. "address proof" → "utility bill").
- **Optional document summary** generated by an LLM, cached.

The `/search` endpoint delivers a **hybrid search** across both clients (weighted FTS via generated `tsvector`) and documents (vector similarity via pgvector cosine + BM25 via tsvector, fused with Reciprocal Rank Fusion). Document ingestion includes chunking, LLM-based enrichment (document context + hypothetical questions), and embedding.

## 3. Embedding model: `text-embedding-3-small`

We use OpenAI's `text-embedding-3-small` via API (requires `OPENAI_EMBEDDINGS_API_KEY`).

| Model | Dim | Status |
|---|---|---|
| **`text-embedding-3-small`** | **1536** | **chosen** |
| `bge-base-en-v1.5` | 768 | considered (local, no API cost) |

**Rationale:** OpenAI embeddings provide higher quality at a reasonable cost for this project scale. The separate `OPENAI_EMBEDDINGS_API_KEY` allows using a different account from the LLM key.

## 5. DB schema

### `clients`
| Column | Type | Notes |
|---|---|---|
| id | UUID PK | server-gen |
| first_name | TEXT | required |
| last_name | TEXT | required |
| email | TEXT UNIQUE | required, indexed |
| description | TEXT | nullable |
| social_links | JSONB | array of strings now → structured objects later; GIN for containment/existence (see §6) |
| search_doc | tsvector | GENERATED ALWAYS AS weighted FTS document (see §6); GIN index |
| created_at | TIMESTAMPTZ | default now() |

No embedding column in v1. No `middle_name` — schema stays `first_name` + `last_name` per TASK.md.

### `documents`
| Column | Type | Notes |
|---|---|---|
| id | UUID PK | server-gen |
| client_id | UUID FK→clients | indexed |
| title | TEXT | required |
| content | TEXT | required |
| created_at | TIMESTAMPTZ | default now() |

Metadata + full content only. Embeddings live in `document_chunks`.

### `document_chunks`
| Column | Type | Notes |
|---|---|---|
| id | UUID PK | — |
| document_id | UUID FK→documents | indexed |
| chunk_index | INT | chunk position within document |
| content | TEXT | chunk text |
| enriched_content | TEXT | content enriched with doc context + hypothetical questions |
| search_text | TEXT | feeds generated `search_doc` tsvector |
| embedding | vector(1536) | text-embedding-3-small dim; HNSW index (cosine) |
| created_at | TIMESTAMPTZ | default now() |

Documents are chunked with `RecursiveCharacterTextSplitter` (chunk_size=500, overlap=50). Each chunk is enriched with an LLM-generated document context sentence + hypothetical questions before embedding.

### Indexes
- `clients`: UNIQUE on `email`; GIN on `search_doc` (generated tsvector) for FTS.
- `document_chunks`: HNSW on `embedding` (cosine); GIN `tsvector` on `search_doc` for BM25.
- `documents`: index on `client_id`.

## 6. Client search — weighted full-text (v1)

Client search uses a **generated weighted `tsvector` column** + GIN index + `websearch_to_tsquery` + `ts_rank`. This replaces the earlier ILIKE/trigram plan — FTS is purpose-built for ranking and handles the TASK.md example (`"NevisWealth"` → client with `john.doe@neviswealth.com`).

`ts_rank` is a **relative ranking value** (which rows are more relevant for this query), not a calibrated confidence or probability. Use it for `ORDER BY`, not as a user-facing confidence metric.

### Generated column + index
```sql
-- 1. Weighted FTS document per client.
--    A = first_name / last_name / email (most important), C = description, D = social_links.
ALTER TABLE clients ADD COLUMN search_doc tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('simple', coalesce(first_name, '')), 'A') ||
    setweight(to_tsvector('simple', coalesce(last_name,  '')), 'A') ||
    setweight(to_tsvector('simple', coalesce(regexp_replace(email, '[@.]', ' ', 'g'), '')), 'A') ||
    setweight(to_tsvector('simple', coalesce(description, '')), 'C') ||
    setweight(to_tsvector('simple', coalesce(
        regexp_replace(regexp_replace(regexp_replace(
            social_links::text,
            '[\[\]\"]', '', 'g'),
            ',', ' ', 'g'),
            '[:/.]', ' ', 'g'),
        '')
    )), 'D')
  ) STORED;

-- 2. GIN index for fast tsquery matches.
CREATE INDEX clients_search_doc_gin ON clients USING gin (search_doc);
```

Notes:
- `'simple'` config — no stemming, just normalization. Right choice for names/emails/URLs where stemming distorts tokens.
- No `lower(...)` before `to_tsvector` — the text-search pipeline normalizes case itself.
- `websearch_to_tsquery` supports quoted phrases, `OR`, and `-` exclusion — user-friendly query syntax.

### Search query
```sql
SELECT *,
       ts_rank(search_doc, websearch_to_tsquery('simple', :query)) AS score
FROM clients
WHERE search_doc @@ websearch_to_tsquery('simple', :query)
ORDER BY score DESC;
```

### `social_links` (JSONB array of strings)

Extracted into `search_doc` by casting to text and stripping JSON brackets/quotes with `regexp_replace`, then tokenizing URLs by replacing protocol/path separators. Weight: D (lowest priority). Note: generated columns cannot use subqueries, so `jsonb_array_elements_text` is unavailable; the `::text` + `regexp_replace` approach is the viable alternative.

## 7. BM25 / lexical search in Postgres

Postgres has **no built-in true BM25**. The current approach uses built-in `tsvector` + `tsquery` + `ts_rank` as a BM25 approximation + GIN index. Three paths for future upgrade:

1. **Built-in FTS** — `tsvector` + `tsquery` + `ts_rank_cd` + GIN index. TF-based, not true BM25, **zero extension**. Good enough for v1/v2.
2. **ParadeDB `pg_search`** — true BM25 via Tantivy (Rust) inside Postgres. Adds a Docker image dependency.
3. **pgvector `sparsevec`** — BM25-like dot product via sparse vectors (requires embedding model that supports sparse, e.g. `bge-m3`).

**Current recommendation:** built-in FTS. Document ParadeDB as a future upgrade.

## 8. Python / FastAPI best practices

- **Virtual environments:** yes — `uv` preferred (fast, modern) over `pip`/`venv`. Docker container IS the isolation in prod; no separate venv inside the image.
- **Dependency mgmt:** `pyproject.toml` (PEP 621) + `uv` lock file.
- **DB layer:** SQLAlchemy 2.0 **async** + `asyncpg` (FastAPI is async-native).
- **Config:** `pydantic-settings` `BaseSettings` reading from `.env`.
- **Lint/format/types:** `ruff`, `mypy`, `pre-commit` hooks.
- **Testing:** `pytest` + `pytest-asyncio` + `httpx` (`AsyncClient`). Test DB via compose.
- **Migrations:** `Alembic`.
- **Container:** multi-stage `Dockerfile`, non-root user, `.dockerignore`.
- **App structure:** app factory (`create_app()`); DI for DB sessions; versioned API `/v1/`; `/health`; structured logging.

## 10. Endpoints & error coverage

| Method | Path | Purpose | Error codes |
|---|---|---|---|
| POST | `/v1/clients` | create client | 422, 409 dup email |
| GET | `/v1/clients` | list clients | — |
| GET | `/v1/clients/:id` | get one client | 404 |
| POST | `/v1/clients/:id/documents` | create doc + embed | 404 client, 422 |
| GET | `/v1/documents/:id` | get one doc | 404 |
| GET | `/v1/documents` | list documents (cursor pagination) | 400 invalid cursor |
| GET | `/v1/search?q=` | **hybrid search** (client FTS + doc RRF) | 400 empty/invalid `q` |

Shared `ErrorResponse` schema declared via FastAPI `responses=` on each route so all error cases appear in `/docs`:

```json
{ "detail": { "code": "CLIENT_NOT_FOUND", "message": "Client not found", "resource_id": "uuid-or-null" } }
```

- `400` empty/invalid `q`
- `404` client/document not found
- `409` duplicate email
- `422` Pydantic validation (auto + declared)
- `500` unexpected
- `503` embedding model not loaded / OpenAI unreachable (summary)

## 12. Constraints to remember

1. **OpenAI key** can only call `gpt-4.1-nano`. No embedding models, no `gpt-4o-mini`. Rotate the key (it was pasted in chat).
2. **Embeddings** use OpenAI `text-embedding-3-small` (1536-dim) via API key. Separate from the LLM key.
3. **No client embeddings** — client search uses weighted FTS via a generated `tsvector` column over first_name/last_name/email/description/social_links (§6).
4. **`document_chunks` table** with real chunking via `RecursiveCharacterTextSplitter` from day one.
5. **v1 `/search` = hybrid: client FTS + document RRF fusion** (cosine similarity + BM25 via tsvector).
6. **`server/` folder** for backend; `frontend/` for UI.
7. **`created_at`** on both clients and documents (TIMESTAMPTZ, default now()).
8. **Swagger must document** 400/404/409/422/500/503 via a shared `ErrorResponse`.
9. **Best practices:** `uv`, async SQLAlchemy, `pydantic-settings`, `ruff`+`mypy`, `pytest`+`httpx`, `Alembic`, multi-stage Dockerfile.
